# Pending

One living list. The `pending` brake checks these rules:

- One card per finding: `- **P-<n>** — <text>. Origin: <where>. Status: <unscheduled | scheduled | in progress on <branch>>.`
- A card is deleted in the commit whose message says `closes P-<n>`.
- A number is never used twice.
- `in progress on <branch>` does not outlive its branch.

## Memory and agents

- **P-223** — `hooks/core/memory.mjs:21` (`rebuild`) runs only `qmd update`, while the recall after a compact asks `qmd query` with a `vec:` part (`:91`) that finds nothing until `qmd embed` has run: recall is by keyword only (`docs/superpowers/specs/2026-11-13-memory-index-design.md:68`), with no message. The remedy: on `sessionEnd`, in the same background job, run `qmd embed` and `qmd cleanup` after the update, under a lock so two sessions never embed at once; `doctor` says when the models are missing (`qmd pull`). Origin: migration plan of the reference project and the owner's question, 2026-11-19. Status: unscheduled.
- **P-224** — `hooks/core/memory.mjs` has no place for a project's own step after the index update, so a project that also exports its sessions to a folder outside the repository keeps a second hook on the same events. The remedy: `memory.after`, a command the hook runs after its update in the same background job. Origin: migration plan of the reference project, 2026-11-19. Status: unscheduled.
- **P-225** — A project that needs a package agent with more effort or extra skills (`implement-sql` at high, `review` with the project's own invariants) must keep its own copy ("keep theirs", `record.kept`, `bin/xworkflows.mjs:538`), and that copy silently gets no later upgrade of the package's agent. The remedy: `agents.<id>.{effort, skills, append}` in the config, applied by install on every upgrade. Origin: migration plan of the reference project, 2026-11-19. Status: unscheduled.
- **P-226** — The `pending` rule 3 (a plan or spec commit with no list change) is checked only at push time (`checks/pending.mjs`), so a project that wants the refusal at commit time keeps its own pre-commit: a second code of the same rule, which can disagree with the brake (it refuses a plan commit on a batch branch that the `--no-ff` merge's list change saves, the case of P-221). The remedy: install a `pre-commit` line that runs rule 3 with the brake's own code on the staged files, letting a merge in progress and a batch branch through. Origin: migration plan of the reference project, 2026-11-19. Status: unscheduled.
- **P-227** — `checks/goal-cited.mjs:7` reads the goals from `docs/BUSINESS.md` by a fixed path, so a project that keeps its goals in another file must keep a second copy that drifts. The remedy: `paths.business`, default `docs/BUSINESS.md`, read through the defaults module by `goal-cited` and by the skills that name the file (`adapt`, `next-step`, `orchestrate`, `plan`). Origin: migration plan of the reference project, 2026-11-19. Status: unscheduled.
