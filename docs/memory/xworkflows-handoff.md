**How it works (as built in handoff-1)**
- The skill `handoff` writes `.xworkflows/handoff.md`. The file is git-ignored and capped at 1500 bytes. Its first line is `main: <sha>`.
- `orchestrate` step 6 writes it at every batch merge. A session that loaded `orchestrate` before the install does not write it.
- The hook `handoff-load` is `hooks/core/handoff-load.mjs` (renamed from `handoff.mjs` in the fix round, with its test). Its manifest id is `handoff-load`, separate from the skill's id `handoff`; before the rename both pieces shared id `handoff` and installed.json kept only one. It compares the first line with the sha of `main`. Since T7/T8 it also requires `HEAD` to be that same sha (owner's answer), at session start and on every PreCompact, so the hand-off stops loading as soon as any new commit lands, on `main` or on the next batch's branch. A hand-off written on a batch branch does not load, because HEAD is not main's sha. Settled by the owner on 2026-11-23 and closed in code by the review of `af38bcb`: off main the skill says `Next: /compact` and that the file will not load (`skills/handoff/SKILL.md` step 1, and its installed copy). Before that the skill still said `Next: /clear`.
- The hook tests the sha before the size. A stale hand-off is silent at any size. A cap that is not a whole number above zero means the default.
- It feeds the hand-off on `PreCompact` (as plain text, so it becomes the summary instructions), on `SessionStart` with source `clear`, and at startup (both as JSON).
- Manual check without losing the session: `echo '{"hook_event_name":"SessionStart","source":"clear"}' | node .xworkflows/hooks/run.mjs claude handoff-load`. Swap the event name for `PreCompact` to see the plain-text form.
- Limit: a commit made after the hand-off is written makes it stale. The skill must be the last step, after every commit.

**Process lessons (what burned turns in handoff-1)**
- An implementer ran `install` on this repo by mistake during T2 and restored it. Check `git status` after each implementer report.
- A report starting with `blocked:` can come from a closed tool stream while the edits are already on disk. Check the files and run the full suite before trusting either the report or a retry. T7 hit this too ("Tool permission request failed: AbortError: Stream closed"): the edits were on disk, but no green run was seen.
- A `grep` that prints nothing and exits 1 means no match, not a pass. Read the pass and fail counts from `node --test`.
- After a dropped connection, check the state first (clean tree, expected commits, seals, cards) and only then continue. The owner asked for exactly this.
- Review rounds: the first confirmation found the doctor problem again. Expect repeats when a check is re-implemented instead of reused.
- A test that cannot fail is no test. The risk review's blocking finding was a doctor measure test with no commit in `repo()`, so it passed on the old code. Check that a new test fails on the old code.
- When a loader gains a condition, check the writer too. The skill kept saying `Next: /clear` after the hook began to require HEAD to match main.
- Two tests repeat the same steps (install, commit, measure, write the hand-off, assert the same line): `bin/doctor-handoff-measure.test.mjs` and `bin/doctor.test.mjs` about lines 189-199. Each runs a full install and doctor. Closed by the review of `af38bcb`, per the owner's answer: `bin/doctor-handoff-measure.test.mjs` is deleted and `bin/doctor.test.mjs:189-208` is kept.
- Hand-editing `manifest.json` leaves the hashes stale. `pack --check` then fails with `manifest.json is stale: run xworkflows pack`, and the full suite is red until `pack` runs (the fix round left this to T6). A fix agent's own last full run had failures, and it did not re-run the suite after its last fix. Run the full suite after `pack`, not before.
- The orchestrating session must wait for the agent's report before it relays or answers. It replied "nothing to relay" while the fix agent was still running. See [[handoff-batch-1]]. The `af38bcb` review repeated it: the orchestrating session answered while the review agent was still running, so the answer had to be checked against the report.
- A reviewer that cannot write outside the repository cannot run a reproduction that writes `.xworkflows/handoff.md`. The `af38bcb` review left that reproduction unrun and listed it under "not checked". Plan a verify agent in a worktree up front.
- Verifying a review finding: a verify agent proved the doctor finding with one red test on a throwaway branch `verify/<id>`, made in a git worktree under `node_modules/.cache/` inside the repo (paths outside the repo are denied). It removed the worktree and kept the branch. It did not run the existing test it was asked about, so say which checks were not run.
- `flow.mjs` does not pass `effort`. Agents run with the effort in their own agent file (`medium` for the implementer that was asked for `high`). Not verified whether the SDK honours it.
- Spend on this batch, from the review ledger `api-reviews-2026-11.json` (separate from `proof-spend.json`): 3.61 USD at the first report, 11.95 USD at merge. One Fable review cost about 5.57 USD. Each agent run had its own cap (5 to 10 USD). See [[no-api-spend]].
- A check that searches free text must not search the text it reads from. The doctor's phrase search matched a hand-off that quoted the phrase (P-219). The fix exports the hook's own sentence and matches only its start.
- A background implement agent that waits on a shell keeps the session busy after the hand-off is written. Before `/clear`, make sure no agent is still alive (owner's correction in session 6c0db597, 2026-11-23). The agent's work was already committed, so nothing was lost there.
- Announcing that the hand-off line will show on `/clear` before a test has shown it on screen repeats the handoff-notice mistake. Check the owner-facing result, not the hook JSON.
