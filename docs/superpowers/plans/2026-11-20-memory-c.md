## Owner's answers

Grill of 2026-11-20:

- C1: one serial background job runs `qmd update`, then `qmd embed`, then `qmd cleanup`. Change detection stays with qmd ("Chain update, embed, cleanup (Recommended)"). Measure whether `qmd embed` with nothing new is fast and whether an interrupted embed keeps its progress; write the numbers in the task report.
- C2: a key `memory.before`, an argument list (`["node", "scripts/export.mjs"]`), runs first in the same job, so what it writes is indexed in the same run ("Before update, same job").
- C3: a small runner script does the job: a lock (a second job finds the lock and exits; a lock older than the step limit is stale), the steps in series, one log line per step. "No limit on embed": `qmd embed` relies on its own `--timeout`; only the `memory.before` step has a limit, 30 minutes (assumed: the owner chose no limit for embed and named none for the step; 30 is qmd embed's own default).
- After the risk review of a4035ce, the owner changed C3's stale rule: "By process: stale only if dead (Recommended)". A lock is stale only when the pid it holds is not alive; a job removes only a lock that holds its own pid. Shared index: "Shared: update only (Recommended)": `embed` and `cleanup` run only on the project's own index (`.qmd/`); on a shared index (`memory.index`, or qmd's default index) only `update` runs, as before. Models: "One rule, embed model only (Recommended)": one test, in the job, used by doctor too; doctor no longer asks for the reranker and the query-expansion models.
- C4: when qmd's models are missing, doctor warns and names `qmd pull`; the job skips `embed` and keeps `update` and `cleanup` ("Doctor warns, embed skipped (Recommended)").
- The job runs on the events it runs on today (preCompact and sessionEnd, `hooks/core/memory.mjs:104`).
