# A user's git hook keeps its name and its place

Card P-46.

## 1. The deepened request

- Request: when a project already has a git hook, `install` adds its check without changing that hook's name or place. Done: a hook that finds its work by its own file name, as the shim of husky does, still works after `install`, proven with a copy of that shim.
- Adds: with `core.hooksPath` set, git stops looking in `.git/hooks` altogether, so the user's other hooks (`pre-commit`, `commit-msg`) stop running unless about 28 hook names are forwarded (https://git-scm.com/docs/githooks, read not tested).
- Adds: husky sets `core.hooksPath` to its own folder on every `npm install`, whatever was there, so a hooks folder of install's own would be taken away silently (https://raw.githubusercontent.com/typicode/husky/main/index.js, read not tested).
- Adds: lefthook and pre-commit refuse to install when `core.hooksPath` is set (their sources, read not tested).
- Material: today `install` renames the user's hook to `<name>.before-xworkflows` and writes a hook that runs it first (`bin/xworkflows.mjs:419-436`, read not tested).
- Material: `doctor` already judges a check line inside a hook it did not write: alone on its line, not commented, before any line that exits, in an executable file (batch 4 of cleanup-b).
- Methods: A, a hooks folder of install's own through `core.hooksPath`. B, nothing moves: one marked line inside the user's hook.

On 2026-11-13 the owner had ruled for A, as the one way that changes neither the name nor the place. With the three facts above put to him the same day, he chose B.

## 2. The rule

The three hooks are the ones of today: `pre-push`, `post-merge`, `post-commit`. The hooks folder is found as today.

1. **Nothing is renamed or moved.** `install` never renames, moves or replaces a hook it did not write.
2. **No hook there, or install's own hook:** as today.
3. **A user's hook that is a shell script** (its first line names `sh`, `bash`, `dash`, `zsh` or `ksh`, or it has no `#!` line and is run by a shell): `install` asks whether to add the xworkflows line to it, and says that the line runs first and the rest of the hook after it. The default answer and `--yes` behave as the chain question does today.
   - Yes: `install` inserts one marked line, after the `#!` line when there is one, else as the first line. Nothing else in the file changes. A second install adds no second line.
   - No: nothing is written, the refusal is recorded as today, and `install` prints the line.
4. **A user's hook that is not a shell script:** nothing is written. `install` prints the line to call from it, and records it as declined.
5. **A hook written by a hook manager:**
   - husky (the hook is its shim, which runs the file of the same name one folder up): the user's hook is that file. Rule 3 applies to it; when it does not exist, a yes creates it with the line alone.
   - lefthook, pre-commit: nothing is written. `install` prints the line and says to add it as a command of that tool for that hook, and records it as declined.
6. **The line.** One physical line that ends with the mark. It runs a file of install's own under `.xworkflows/`, and does nothing where that file does not exist, so a clone without xworkflows is not broken by it.
   - `pre-push`: the check runs first, with the pushed refs that git gives on standard input. A failed check stops the push with the check's exit code, before the user's hook runs. After a passed check the rest of the user's hook receives the same standard input, byte for byte, and the same arguments.
   - `post-merge`, `post-commit`: install's part runs first and can never stop or fail the user's hook.
7. **`doctor`** (as today, `pre-push` only): ok when the hook git will run is install's own, or holds the line where it will run, by the rule it already has. For husky's shim it looks in the file one folder up. Otherwise it fails, and the fail line gives the line and the file to put it in.
8. **`uninstall`:** removes install's own hooks as today. From a user's hook it removes the marked line and nothing else, when the line is still what install wrote; a line the user changed stays and is named. The hook is then byte for byte what it was before `install`.
9. **Projects chained the old way** (a `<name>.before-xworkflows` file beside install's chained hook, recorded or not): the next `install` removes its chained hook, gives the user's file its name back, inserts the line with no question (the owner said yes when it was chained), and says so in one line. `uninstall` of an install that was never migrated still restores the old file, as today.

## 3. Tests the change must bring

- A copy of husky's shim and its dispatcher: after `install`, a real push runs the user's hook, found by the hook's own file name.
- A user's `pre-push` that reads its standard input gets the pushed refs, and the check gets the same.
- A failed check stops the push before the user's hook runs.
- A user's hook that ends with `exit 0` still runs the check.
- A hook that is not a shell script is left byte for byte.
- `install` twice: one line. `uninstall`: the hook is byte for byte as before `install`.
- An install chained the old way is migrated; its user's hook has its name back and holds the line.
